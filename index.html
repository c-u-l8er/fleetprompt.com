The trust problem

Discovery is solved. Behavior is not.

The agent ecosystem does not lack directories. Community hubs index tens of thousands of MCP servers; the official MCP registry — still in preview as of mid-2026 — authenticates the namespace you publish under; curated skill marketplaces run security scans on listings. All of it is useful, and all of it is provenance: who published, whether it scans clean, how many people starred it.

None of it is behavior. A namespace check verifies who you are, not what the thing does. A security scan reads the code at rest, not the run. A trust score is a declaration — a number someone's pipeline asserted about a thing you cannot re-derive. We want the layer underneath a declaration: a run you can re-run. That layer exists in alpha, on the machinery this stack already builds. The registry around it does not exist yet — and we know the shape of the thing we are replacing precisely because we built one: the marketplace this domain serves today computes trust from four weighted signals and cannot tell you what any listed agent actually did. This page will keep saying so until the replay gate lands.

The receipt

What a film is, and what replaying it proves.

The evidence bundle is a film, sealed by trvs — the TRAAVIIS verifier. A listing on this registry is a manifest plus a film, and the install path runs through the film, not around it.

  • Inputs are captured at the boundary. The world (what the agent claims to do) and the scenario (what a particular run fed it) are different documents, and mixing them is a typed rejection. Model output enters as a claim, canonicalized at OBSERVE — so the film stays byte-exact even though the model behind it is not deterministic.
  • The reduction is schedule-independent. TRVM reduces by local rewrites on the interaction calculus, so replay order cannot change the answer. That property is what makes "replay it yourself" a coherent offer instead of a hope.
  • Replay derives the identity. Your machine replays the bundle and derives a sem- string. It equals the listing's identity or it does not. A failed replay is a failed install — there is no third state to argue about in a review thread.
  • What it does not prove. A replay shows what ran, not that it should. A faithful film of a harmful agent is still harmful. Films make review checkable; they do not make review unnecessary.
The substrate

Installed onto an image that boots, by a fleet layer that ships.

A registry needs somewhere for the install to land. This one has the unusual advantage that its runtime substrate is the part that already exists — built and measured next door at computedriven.com.

  • T&R is the golden image. A FreeBSD 15 distribution assembled from pkgbase: 364 MB, 50 packages in the server flavour, and 51 MB written on first boot where a stock cloud image writes about 3 GB. Patching is a build-time job, done once.
  • PARKVPS is the fleet layer. QEMU/KVM with no root, no libvirt, and no daemon you have to trust — one process per instance, all state on disk as JSON, and every disk a copy-on-write overlay on the one shared golden image. Spawning an instance costs kilobytes.
  • So an install is an overlay. The end state of install is not a package scattered into your system — it is a fresh guest booted from the golden image with the agent's bundle aboard, disposable by deleting one overlay file.
  • The honest gap: the runtime and verifier are not in the T&R build yet. They run on a booted image because we copied them there by hand. Until the build ships them, everything above the substrate is a demonstration, not a download.
The install path

Three commands. None of them replay yet.

This is the designed flow, numbered because the order is the point. An install engine already exists and runs all seven of its steps — permission review, manifest verification, dependency resolution, policy check, deploy, connect, audit. Not one of them is a replay. The tags on the right are the truth about each step today.

01 Publish. Seal the run into a film with trvs; push manifest and bundle to the registry. The sealing half runs today, at alpha. The pushing half has a registry to push to and nowhere in it to put a film. gate not built
02 Verify. Your machine replays the bundle and derives the identity. Equal to the listing's string, or the install stops. The underlying replay-and-derive has been measured once, across two operating systems. cli not built
03 Run. PARKVPS boots a copy-on-write overlay on the T&R golden image with the verified bundle aboard. The substrate for this step ships; the wiring from step 02 into it does not exist. substrate ships
Why publish a flow that isn't code? Because the design constrains the build, and publishing it lets you check the build against it later. When the CLI lands, this section becomes a transcript instead of a drawing — and if the transcript disagrees with the drawing, that will be written here too.

Open

What doesn't work yet, on the same page as what does.

A marketplace page that only shows wins is asking you to shop on faith. These are the current holes, at the size they actually are.

A replay proves what ran, not that it's safe

Identity is not harmlessness. A faithful bundle of a bad agent replays perfectly. Films make review checkable — a human still has to do the reviewing.

One implementation

"Same identity on two machines" currently means one codebase agreeing with itself. A registry whose trust math rests on one program has a single point of semantic failure.

The stack is not in the build

Runtime and verifier were copied onto the booted image by hand. Until the T&R build ships them, "install to the substrate" is a demonstration, not a download.

Permissions are declared, not derived

What an agent may touch is still a human-written manifest. Deriving least-privilege from the film itself is an idea we like and a feature that does not exist.

Economics unpriced

Films have weight. Hosting bundles, replay compute, who pays for verification bandwidth — unanswered. A registry with no cost model is a demo of a registry.

A registry of one is a ledger

The count on this page is one, and the one is ours. Until a second publisher seals a listing we did not write, this is a ledger, not a market.

The registry above shows its true contents: one entry, sealed by us, not installable. When that changes, the count changes — nothing else on this page is allowed to change it.
Clarity

What FleetPrompt is, and is not.

It is

  • A registry design — manifests plus replayable films, with install gated on replay
  • Built on machinery that runs — trvs at alpha, T&R and PARKVPS shipping
  • Mechanical about trust — an identity you derive, never a score you're told
  • Part of one stack — specs at specprompt.com, substrate at computedriven.com

It is not

  • Launched — there is no waitlist because there is nothing to wait for yet
  • A model hub — no weights, no checkpoints
  • A prompt library — listings carry films, not vibes
  • A safety authority — replay proves fidelity; judgment stays with the person installing
Follow the work

The registry will grow in the open, gated behind the same rule as this page: counts are real or they are absent. If you ship agents and the trust problem costs you — tell us what a receipt would need to contain before you'd stake an install on it. That answer shapes the manifest format.
